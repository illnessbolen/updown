# Polymarket Up/Down — латентный арбитраж (фазы 1–3: данные и P(fair), paper-исполнение и риск, статистика)

Исследовательский бот для рынков Polymarket «BTC/ETH/SOL/XRP/DOGE/BNB Up or Down»
(5m, 15m, 1h, 4h, daily). Идея: спот на CEX двигается раньше, чем перестраивается книга
Polymarket; если справедливая вероятность исхода, посчитанная по живому споту, заметно
отличается от цены в книге **после комиссий и проскальзывания**, — это сигнал.

> **Статус.** Фаза 1: data ingestion, модель справедливой вероятности, сигналы, запись тиков,
> бэктест сигнального слоя. Фаза 2: **paper-исполнение** (симуляция ордеров против живой книги
> Polymarket, виртуальный баланс) и **риск-менеджмент** (профили с жёсткими границами,
> Kelly-sizing, kill-switch, circuit breaker, дневной стоп, cooldown). Фаза 3: **статистика**
> (винрейт против безубыточного, P&L, просадка, Sharpe-подобные метрики), **проверка гипотезы**
> о наличии edge с учётом асимметрии выплат и **еженедельный отчёт**.
> **Реальных ордеров эта версия отправить не может** — боевого режима в коде нет.
> Дальше — боевой режим по явному решению (фаза 4: только с `DRY_RUN=false` **и** флагом
> `--i-understand-the-risk`, с проверкой баланса/allowance).

Прежний бот v7 (REST-поллинг, snipe/arb) лежит без изменений в `legacy/bot_v7.py` —
как референс для фазы исполнения (py-clob-client, maker-first, fee-модель, FIX 1/2/3).

## Запуск одной командой

Нужен только Python 3.10+. Скачайте/распакуйте папку и в терминале:

```bash
cd updown-bot
./start.sh              # Linux / macOS: меню (discover, shadow, paper, analyze, stats, hypothesis, report, test)
./start.sh paper        # или сразу нужный режим с любыми аргументами bot.py
```

```bat
cd updown-bot
start.bat               :: Windows (cmd): то же меню;  start.bat paper  — сразу режим
```

При первом запуске скрипт сам создаёт окружение `.venv`, ставит зависимости из
`requirements.txt` и копирует `.env.example` в `.env` (там меняются настройки). Повторные запуски
стартуют сразу. `./start.sh test` прогоняет тесты — удобная проверка, что всё установилось.
Остановка shadow/paper — Ctrl+C; экстренная остановка ордеров — создать файл `STOP` в папке
(`touch STOP`, в Windows `type nul > STOP`).

## Быстрый старт (вручную)

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt            # + requirements-dev.txt для тестов
cp .env.example .env                       # при необходимости поправить

python bot.py discover                     # какие Up/Down окна сейчас активны (Gamma)
python bot.py shadow --record              # живые фиды → P(fair) → data/signals.csv; тики → data/ticks/
python bot.py paper --record               # shadow + симуляция исполнения с виртуальным балансом
python bot.py paper --reset                # новый paper-счёт (старое состояние сохраняется в .bak)
python bot.py resolve                      # дотянуть исходы окон из Gamma (shadow/paper делают это сами)
python bot.py analyze                      # калибровка модели, теневые сигналы, результаты paper
python bot.py stats                        # метрики закрытых сделок + разбивки (актив, длительность, цена, τ…)
python bot.py hypothesis                   # отличим ли edge от нуля (с учётом асимметрии выплат)
python bot.py report                       # еженедельный отчёт сейчас (работающий бот пишет его сам раз в 7 дней)
python bot.py replay data/ticks            # бэктест сигнального слоя на записанных тиках
python bot.py replay data/ticks --paper    # + бэктест исполнения (свежий счёт, отдельный каталог)
python bot.py price --spot 100010 --ref 100000 --tau 30 --sigma-bps 1.0   # разовый расчёт P(fair)

touch STOP                                 # kill-switch: новые ордера не отправляются, висящие снимаются

pytest -q                                  # 125 тестов
```

Рекомендуемый порядок работы (как в ТЗ): **record/shadow на живом фиде → replay/analyze →
paper на живом фиде + `replay --paper` для A/B настроек → и только по явному решению — боевой режим.**

## Модель справедливой вероятности

Контракт платит 1, если **цена источника резолюции в момент закрытия окна ≥ цене в момент
открытия** (ничья → Up). Значит важно не то, что цена «недавно выросла», а **насколько далеко
она сейчас от референса в единицах оставшейся неопределённости**.

Путь цены разбит в момент «сейчас» (это и есть «broken Brownian motion» из ТЗ — в моей
интерпретации): отрезок `[start, t]` уже реализован и целиком сводится к текущей цене `S_t`;
отрезок `[t, end]` ещё случаен и моделируется броуновским приращением. Отсюда:

```
x   = ln(S_t / K)                 K — цена источника резолюции на старте окна
v   = σ² · τ                      τ — секунд до закрытия, σ — вол. ln-цены на √секунду
η   = шум оракула                 std расхождения цены резолюции и нашей оценки S_t
d   = (x − v/2) / √(v + η²)       −v/2: цена — мартингал (нулевой дрейф)
P(Up) = F(d),  P(Down) = F(−d)    F — N(0,1) или Student-t с единичной дисперсией
```

При `F = Φ` и `η = 0` это ровно цифровой опцион Блэка–Шоулза `N(d₂)` при r = 0. Отличия от
наивной версии — осознанные:

| компонент | зачем |
|---|---|
| **τ в знаменателе** | одно и то же движение почти решает исход за 5 с до конца и почти ничего не значит за час (таблица ниже). Длительность окна входит через τ: у дневного окна при том же движении P ближе к 0.5. |
| **σ из тиков этой же WS-сессии** | цена Binance сэмплируется на сетке 1 с (previous-tick), две EWMA квадратов доходностей: быстрая (½-жизнь 2 мин) и медленная (30 мин), с bias-коррекцией на прогреве. Пока не набрано `VOL_MIN_SAMPLES` доходностей — окно не оценивается вовсе. Никаких констант. |
| **σ на нескольких масштабах** | та же оценка ведётся на доходностях за 1 с, 10 с и 60 с (`VOL_SCALES_S`). Окно, где осталось τ секунд, оценивается σ с самого длинного масштаба ≤ τ: для 4 минут до конца — с минутных движений, для 5 секунд — с секундных. Причина: дисперсия секундных доходностей не обязана линейно переходить в минутную (в спокойные периоды котировки «липнут», в движении — тренд), и секундная σ может сильно занижать неопределённость на минутах. Масштаб используется после `VOL_SCALE_MIN_OBS` доходностей; если горизонту нужен ещё не прогретый масштаб (для 60 с — первые ~20 минут), окно не оценивается (`vol_warmup_long`). |
| **согласование с горизонтом на 1 с** | для коротких τ: `σ²(τ) = w·σ²_fast + (1−w)·σ²_slow`, `w = exp(−τ/VOL_FAST_HORIZON_S)`. |
| **полоса σ** | от минимума до максимума по **всем** масштабам и быстрой/медленной оценкам, расширенная на `SIGMA_UNCERTAINTY`; решение принимается по **худшему для стороны** концу полосы (`edge_cons`). Если масштабы расходятся, полоса широкая, и «уверенный» сигнал на фаворита не проходит. |
| **толстые хвосты (TAIL_DOF=5)** | 4σ-движение за секунды в крипте — не событие «1 на 30 000». При x=+20 bp, τ=30 с: Гаусс даёт 0.99987, t(5) — 0.99736. Для покупки фаворита по 0.99 это разница между «edge» и его отсутствием. |
| **шум оракула η** | мы видим Binance, а резолвится по Chainlink. Даже при τ→0 исход не детерминирован, если S в 1–2 bp от K. η = σ базиса ln(Chainlink/Binance), измеренного в совпадающие моменты времени. |
| **единицы источника резолюции** | для Chainlink-окон `S = binance_mid · exp(среднее ln(Chainlink/Binance))`: быстрый Binance переводится в единицы оракула (убирает USDT/USD-премию и систематический сдвиг агрегатора). |

P(Up) при σ = 1 bp/√с (≈ 56 % годовых, типично для BTC), t(5), η = 0:

| x \ τ | 5 с | 30 с | 60 с | 120 с | 300 с | 900 с | 3600 с |
|---|---|---|---|---|---|---|---|
| +0 bp | 0.500 | 0.500 | 0.500 | 0.500 | 0.500 | 0.499 | 0.499 |
| +2 bp | 0.850 | 0.671 | 0.624 | 0.588 | 0.556 | 0.532 | 0.515 |
| +5 bp | 0.983 | 0.854 | 0.779 | 0.709 | 0.637 | 0.580 | 0.539 |
| +10 bp | 0.999 | 0.967 | 0.922 | 0.854 | 0.755 | 0.657 | 0.579 |
| +20 bp | 1.000 | 0.997 | 0.990 | 0.967 | 0.902 | 0.785 | 0.656 |

Граничные случаи зафиксированы тестами (`tests/test_pricing.py`): S = K и τ→0 ⇒ P→0.5
(монотонно); большое отклонение и τ→0 ⇒ P→0 или 1; τ = 0 и η = 0 ⇒ детерминированно,
ничья → Up; точное значение Φ(1) при d = 1; тождество отражения; монотонность по S и τ;
Student-t против замкнутых форм ν = 1, 2.

### Референсная цена (price to beat)

| источник резолюции | окна | как получаем K | `ref_source` |
|---|---|---|---|
| Gamma публикует price-to-beat | любые | берём как есть (появляется примерно через минуту после старта окна) | `gamma_price_to_beat` |
| Chainlink, резолв по TWAP (с 2026-08-07) | 5m, 15m, 4h (`{asset}-updown-…`) | TWAP Chainlink за `twap_s` секунд до старта окна: среднее посекундных тиков RTDS (в каждой секунде — последний известный тик). Так считается и официальный strike: «TWAP … в начале интервала» | `chainlink_twap` |
| Chainlink, резолв по споту (до 2026-08-07) | 5m, 15m, 4h | тик Chainlink из RTDS с меткой = старт окна (история 5 ч) | `chainlink_rtds` / `…_nearest` |
| Binance | 1h (`bitcoin-up-or-down-…-10am-et`) | open свечи Binance: сначала первая сделка минуты из WS (предварительно), затем REST `klines` (авторитетно) | `binance_trade_stream` → `binance_kline` |
| не распознан | — | окно обнаруживается и логируется, но не оценивается | — |

Правило резолва окна берётся из Gamma: `cryptoMarketConfig` (`twapEnabled`, `twapLookbackSeconds`), иначе по
TWAP-потоку в `resolutionSource` (`…-twap-60s-streams`) → `MarketWindow.twap_s`. Окна без этих полей (например,
в записях, сделанных до появления `twap_s`) получают правило по датам смены: с 2026-08-07 TWAP 60 с, у 5m до
2026-08-14 — 30 с (`markets.settlement_twap_s`). На записи 2026-10-02 (31 окно BTC 5m/15m) TWAP из тиков RTDS
отличался от официального `priceToBeat` на 0.09 bps в медиане (максимум 0.45); тик на старте, который бот брал
раньше, — на 2.1 bps (максимум 13.4), для окна 5m это десятки центов справедливой цены.

Если бот подключился к окну после старта и тика на старте нет — окно не оценивается до
конца (`reference_missing`): подставить K по более поздней цене значит оценивать другой контракт.
Для TWAP-окна нужна вся минута тиков до старта (пропуск дольше `ORACLE_STALE_S` → `reference_missing`).

## Сигнал

Для каждой стороны:

```
ask       = min(лучший ask своей книги, 1 − лучший bid противоположного исхода)   # mint-матчинг CTF
fee       = TAKER_FEE_RATE · (ask·(1−ask))^FEE_EXPONENT     (per-market feeSchedule из Gamma приоритетнее)
cost      = ask + fee + EXPECTED_SLIPPAGE
edge      = P_fair(side) − cost
edge_cons = P_fair(side при худшей σ) − cost
SIGNAL    ⇔ edge_cons ≥ EDGE_THRESHOLD  и не сработал ни один гейт
GATED     ⇔ edge_cons ≥ EDGE_THRESHOLD, но гейт сработал (логируется — это материал для анализа ложных срабатываний)
```

Комиссия считается тейкерская (консервативно): maker-first исполнение в фазе 2 может
получить лучше, но решение не должно на это опираться.

Гейты (`reasons` в логах):

| гейт | смысл |
|---|---|
| `spot_stale` | котировка Binance по активу старше `SPOT_STALE_S` |
| `oracle_missing/stale/basis_warmup` | Chainlink-фид отсутствует/молчит/базис не прогрет |
| `sanity_missing/stale/warmup/unavailable` | нет независимой котировки Coinbase (у BNB её нет по умолчанию) |
| `sanity_divergence` | Coinbase и Binance разошлись **в совпадающий момент времени** сильнее нормы → окно пропускается до конца (не дольше `SANITY_BLOCK_MAX_S`) |
| `sanity_unconfirmed` | сразу после резкого движения Binance Coinbase ещё не успел тикнуть; временный гейт, снимается при подтверждении |
| `edge_not_latency` | расхождение не объясняется недавним движением цены (см. ниже) |
| `book_missing/stale/crossed` | нет свежего снапшота книги, CLOB-соединение молчит, книга скрещена |
| `min_time_left/max_time_left` | окно слишком близко к закрытию / слишком далеко |
| `clock_skew` | локальные часы расходятся с Binance > `MAX_CLOCK_SKEW_MS` |
| `resolution_unknown`, `market_closed`, `no_ask`, `ask_out_of_range` | говорят сами за себя |

**Проверка «это латентность»** (`REQUIRE_LATENCY_EXPLANATION`, по умолчанию включена). Стратегия
зарабатывает, только если рынок **отстаёт**: цена уже сдвинулась, а книга Polymarket ещё показывает
старое. Тогда текущая цена рынка должна совпадать с тем, что наша же модель показывала 1–5 секунд
назад (`LATENCY_LOOKBACKS_S`). Модель пересчитывается на цене Binance в эти моменты. Если ни один
момент не совпадает с серединой рынка с точностью `LATENCY_MATCH_TOL` (или полуспреда), то рынок
расходится с моделью вообще: в волатильности, в стартовой цене или он просто **опережает** наш фид.
Такой «перевес» — не латентность, и сигнал блокируется. Так были отсеяны оба ложных сигнала из
первого живого запуска: рынок продавал Up по 0.35, пока наша цена стояла на K, и через 3 секунды
BTC действительно упал.

Для диагностики в `signals.csv` и снапшоты пишутся: масштаб σ (`vol_scale_s`), середина рынка с
учётом комплемента (`mkt_mid_up`), **σ, которую закладывает рынок** (`sigma_implied_bps` — при
нашей цене и K; пусто, если рынок по другую сторону от 0.5), положение цены, которое подразумевает
рынок при нашей σ (`x_implied_bps`), и совпадение с запаздывающей моделью (`lag_match_err`,
`lag_match_s`). `analyze` сводит это в раздел «model vs market»: медиана отношения σ рынка к нашей
по корзинам τ и медианный сдвиг ln(S/K). Отношение сильно больше 1 — модель недооценивает
неопределённость. Устойчивый сдвиг x — проблема со стартовой ценой или пересчётом спота.

Про разделение `sanity_divergence` / `sanity_unconfirmed`: сквозной тест показал, что
наивная проверка «Coinbase ≠ Binance прямо сейчас» срабатывает ровно в момент, когда
появляется латентная возможность (Coinbase тикает реже и отстаёт на доли секунды), и
убивала бы все целевые сигналы. Поэтому «плохие данные» определяются по совпадающим
моментам, а отставание — это временное «не подтверждено».

Окна, где не хватает базовых входов (спот, K, прогретая σ), не оцениваются вовсе; причины
считаются в `unpriced` статусной строки.

## Исполнение (paper)

Каждый SIGNAL предлагается конвейеру исполнения (`execution/pipeline.py`); его ответ пишется в
`signals.csv` (`exec_status`: `queued` или причина отказа).

```
1. одна попытка на окно/сторону одновременно, пауза EXEC_RETRY_S между попытками;
   пока летит ордер на одну сторону, другая сторона того же окна не торгуется
2. RiskManager.pre_trade: kill-switch, circuit breaker, дневной стоп, cooldown, лимит заливок,
   противоположная позиция, свободная экспозиция
3. лимит-цена: максимальная цена на сетке тика, при которой P_cons − цена − fee ≥ MIN_EDGE_AT_FILL,
   и не выше ask сигнала + MAX_SLIPPAGE
4. размер: дробный Kelly внутри потолков (ниже); худший случай резервируется в экспозиции
5. перечитывание книги: REST GET /book обоих исходов (live) / локальная книга после
   симулированной задержки (replay)
6. модель пересчитывается на СВЕЖЕЙ книге: должен остаться SIGNAL на ту же сторону; цена не
   старше BOOK_MAX_AGE_MS (1.5 с); размер пересчитывается
7. бюджет задержки: от получения фрейма, породившего сигнал, до передачи ордера ≤ LATENCY_BUDGET_MS,
   иначе сигнал СБРАСЫВАЕТСЯ (не исполняется «как есть» по устаревшей цене); факт пишется в orders.csv
8. maker_first: GTC-бид на тик ниже ask (и не выше P_cons − MIN_EDGE_AT_FILL), комиссия 0;
   по таймауту MAKER_TIMEOUT_MS — отмена и taker-фолбэк ТОЛЬКО через новую оценку сигнала
   (свой бюджет, своя свежая книга). taker: FAK по лимит-цене.
9. фактические заливки → позиция; исход окна из Gamma → реализованный P&L
```

**Как симулируются заливки** (`execution/paper.py`). Ордер встречает книгу в том виде, в каком
она будет через `PAPER_FILL_DELAY_MS` после отправки (время доставки + задержка нашего фида), —
если более быстрые участники забрали котировку, paper-ордер тоже её не получит. Taker проходит
по асскам своего токена и по комплементу (1 − бид противоположного исхода) до лимита; комиссия
по каждому уровню. Maker: пересекающаяся часть исполняется сразу как taker; остаток стоит и
заливается только при свидетельстве продавца — появился ask на нашей цене или ниже, сделка
ниже нашей цены, сделки по нашей цене сверх объёма, стоявшего впереди в очереди. Заливка
запоминается на `PAPER_LIQUIDITY_MEMORY_S`, чтобы следующий paper-ордер не «купил» ту же
котировку повторно. Бид снимается, как только модель или гейт говорят, что edge ушёл.

**Ограничения симуляции**: нет конкуренции в очереди сверх видимой книги и нет отказов биржи.
Paper P&L — оценка сверху для живой торговли.

Про maker-first: в латентном арбитраже котировку, на которую приходит сигнал, обычно быстро
забирают, а мейкер-бид заливается чаще всего тогда, когда цена идёт против него. Режим включён
по умолчанию, как в ТЗ, но `orders.csv` и `analyze` разделяют maker и taker. Сравнить на одной
записи можно так: `replay --paper` с `EXECUTION_STYLE=maker_first` и с `EXECUTION_STYLE=taker`.

## Риск-менеджмент

**Профили** (`RISK_PROFILE`), всё — доли **текущего** банкролла (кэш + деньги в открытых позициях
по себестоимости), не фиксированные суммы:

| профиль | макс. ставка | макс. экспозиция | дневной стоп | доля Kelly | заливок на окно/сторону |
|---|---|---|---|---|---|
| conservative (по умолчанию) | 1 % | 10 % | 3 % | 0.10 | 1 |
| moderate | 2 % | 15 % | 5 % | 0.25 | 2 |
| aggressive | 4 % | 25 % | 8 % | 0.40 | 3 |
| **жёсткие границы** | 0.1–5 % | 1–30 % | 0.5–10 % | 0.01–0.50 | 1–5 |

Значения профиля можно переопределить (`RISK_BET_PCT`, `RISK_EXPOSURE_PCT`, `RISK_DAILY_STOP_PCT`,
`RISK_KELLY_FRACTION`, `RISK_MAX_FILLS_PER_SIDE`), но только внутри жёстких границ: они — константы
в `risk/limits.py`, а не настройки. Выход за границу останавливает запуск с ошибкой.

**Kelly-sizing.** Покупка акции по полной цене c (ask + fee + slippage) с вероятностью выигрыша p —
ставка с полным Kelly `f* = (p − c) / (1 − c)`. Берётся p = P(fair) на консервативном краю
полосы σ и только доля `kelly_fraction` от f* (не больше 0.5 — полный Kelly на оценённом p
слишком волатилен). Порядок: `stake = kelly_fraction·f*·bankroll`, потом `min(stake, max_bet,
свободная экспозиция)`; меньше минимума биржи (`orderMinSize`, `MIN_ORDER_USDC`) — поднимается до
минимума, только если минимум сам помещается под потолок, иначе сделки нет. Kelly работает
**внутри** лимитов, не поверх них. В `orders.csv`: `kelly_full`, `kelly_stake`, `cap`, `sized_by`
(`kelly` / `max_bet` / `exposure` / `exchange_min`).

**Остановки и отказы**

| механизм | поведение |
|---|---|
| kill-switch | файл `KILL_SWITCH_FILE` (по умолчанию `STOP` в рабочем каталоге): новых ордеров нет, висящие снимаются; при запуске с файлом бот отказывается стартовать |
| circuit breaker | `MAX_CONSECUTIVE_ERRORS` ошибок исполнения подряд (сбой REST-книги, внутренняя ошибка) → стоп до перезапуска |
| дневной стоп | P&L дня ≤ −`daily_stop_pct` × банкролл на начало UTC-дня → стоп до следующего дня. P&L дня = реализованные расчёты + **предварительные убытки**: окно закончилось, и наша цена оракула на закрытии уже показывает проигрыш (> 2 bp от K), а Gamma ещё не зарезолвила. Предварительные выигрыши не учитываются. |
| cooldown | после убыточной сделки (и после предварительного убытка) актив не торгуется `COOLDOWN_AFTER_LOSS_S` |
| лимиты позиции | заливок на окно/сторону ≤ профиля; обе стороны одного окна не держатся (`ALLOW_BOTH_SIDES=false`) |

Состояние paper-счёта (`data/paper_state.json`: кэш, позиции, P&L дня, cooldown) сохраняется
после каждого изменения: перезапуск не обнуляет дневной стоп и cooldown. Позиции, чьи окна
зарезолвились, пока бот был выключен, рассчитываются при старте.

**Предстартовая проверка** paper: kill-switch отсутствует, банкролл > 0, профиль внутри границ;
печатаются эффективные лимиты в USDC. Проверка баланса и allowance на кошельке относится к
боевому режиму (фаза 4).

## Источники данных

| фид | что | живость |
|---|---|---|
| Binance `wss://stream.binance.com:9443/stream` | `bookTicker` + `trade` по всем активам в одном соединении | protocol ping; 24-часовой разрыв Binance переживается переподключением |
| Coinbase `wss://ws-feed.exchange.coinbase.com` | `ticker` + `heartbeat` (публичные) | heartbeat раз в секунду |
| Polymarket RTDS `wss://ws-live-data.polymarket.com` | `crypto_prices_chainlink` — источник резолюции 5m/15m/4h | текст `PING` каждые 5 с |
| Polymarket CLOB `…/ws/market` | `book`, `price_change` (обе версии формата), `tick_size_change`, `last_trade_price` | текст `PING` каждые 10 с |
| Gamma REST | discovery и исходы | urllib3 Retry; при недоступности раунд прерывается |

Все WS: переподключение навсегда с экспоненциальным backoff + full jitter (счётчик попыток
сбрасывается только после реально полученных данных), watchdog тишины
(`WS_SILENCE_RECONNECT_S` без единого фрейма → соединение пересоздаётся), ошибки
обработчика не роняют фид. Staleness для торговли решает движок — по каждому источнику и
каждому активу отдельно.

Книги Polymarket: при переподключении все книги сбрасываются и ждут новый снапшот; дельты
до снапшота игнорируются. При смене окна токены добавляются на живом соединении
(`"operation": "subscribe"`); если снапшот не пришёл за `POLY_SNAPSHOT_TIMEOUT_S` — полное
переподключение, после 3 неудач подряд — режим «переподключение при каждой смене».
Подписка делается за `DISCOVERY_PREFETCH_S` до открытия окна, так что к старту книга уже есть.

### Discovery

* **Детерминированные** 5m/15m: `{asset}-updown-{5m|15m}-{unix_start}` для текущего и
  следующего окна — прямой запрос раз в `DISCOVERY_TICK_S`, отрицательный кэш для ещё не
  выставленных слагов.
* **Скан** раз в `DISCOVERY_SCAN_INTERVAL_S` (60–300 с): Gamma `/events`, тег `crypto`,
  окончание в ближайшие `GAMMA_SCAN_HORIZON_H` часов, фильтр `updown|up-or-down|up or down`.
  Распознаются `…-updown-4h-{unix}`, часовые `bitcoin-up-or-down-{month}-{day}[-{year}]-{h}{am|pm}-et`
  (ET с учётом перехода на летнее время) и дневные `…-up-or-down-on-{month}-{day}`.
* Токены сопоставляются **по названию исхода** (`Up`/`Down`), а не по позиции в массиве.
* Кэш с TTL до конца окна; каждое окно живёт на своей временной шкале.
* Нераспознанный слаг или несовпадение времени конца со слагом → окно отклоняется с
  причиной в логе, а не угадывается.

## Логи и анализ

`data/signals.csv` — каждый SIGNAL/GATED (дедупликация: не чаще раза в `SIGNAL_RELOG_S`
на окно/сторону, если edge не сдвинулся на `SIGNAL_RELOG_EDGE_DELTA`). Поля: спот Binance
и в единицах оракула, K и его источник, τ, x, σ и её полоса, η, d, P(fair) и его полоса,
сторона, P(market) = ask (и откуда он), fee, slippage, cost, edge, edge_cons, порог,
гейты, возраст спота/оракула/книги, **задержка детекции** (от получения фрейма до
решения), `executed` (в этой фазе всегда 0).

`data/snapshots-YYYYMMDD.csv` — модель против рынка для **каждого** оцениваемого окна
(~20 точек на окно, чаще к закрытию), независимо от сигналов: материал для калибровки и
поиска пропущенных возможностей.

`data/outcomes.csv` — победитель каждого окна из Gamma. PnL сигнала получается join'ом
(`bot.py analyze` пишет `signals_resolved.csv`), файлы только дописываются.

`data/orders.csv` (paper) — каждая попытка исполнения, отправленная или сброшенная: причина
(`latency_budget_exceeded`, `stale_book`, `signal_gone_after_refresh`, `refresh_failed`, …),
тип (maker/taker/фолбэк), запрошено/залито, средняя цена, комиссия, Kelly и что ограничило
размер, `t_trigger`/`t_send`, **фактическая задержка сигнал→отправка**, задержка и источник
перечитывания книги, возраст использованной цены. Связь с `signals.csv` — по `signal_id`.

`data/settlements.csv` (paper) — каждая закрытая позиция: доли, средняя цена, комиссии,
maker/taker, победитель, выплата, реализованный P&L, P&L дня.

`bot.py analyze` выводит:
* модель против рынка: какую σ закладывает рынок относительно нашей (по корзинам τ) и сдвиг ln(S/K);
* Brier / log-loss P(fair) против mid рынка на тех же строках, по корзинам τ, и таблицу
  надёжности. Строки внутри окна сильно коррелированы — эффективный размер выборки ≈ число окон.
* теневые SIGNAL и отдельно GATED: первый сигнал на окно/сторону как гипотетический taker-fill;
  винрейт **рядом с безубыточным винрейтом** (= средняя цена входа), средний/медианный PnL, ROI.
* paper: отправлено/сброшено по причинам, задержка p50/p95, fill ratio, винрейт закрытых
  позиций против безубыточного, P&L, ROI, доля maker; в `signals_resolved.csv` добавляются
  статус и объём исполнения каждого сигнала.
* при n < 100 — явное предупреждение о недостаточности данных.

О винрейте: покупка по 0.97–0.99 требует 97–99 % побед только чтобы выйти в ноль. Высокий
винрейт на таких ценах совместим с нулевым или отрицательным edge; проверять нужно PnL
против цены входа, а не винрейт — это делает `bot.py hypothesis` (ниже).

## Статистика и проверка гипотезы

**Сделки** берутся из логов (`--source`):
* `paper` — закрытые paper-позиции (`settlements.csv`), к ним подтягиваются вероятность модели на
  момент отправки (`orders.csv`), время до закрытия (`signals.csv`), maker/taker;
* `shadow` — первый SIGNAL на окно/сторону как гипотетическая покупка 1 акции по ask + fee + slippage;
* `auto` — paper, если есть закрытые позиции, иначе shadow. `--days N` — только последние N дней.

**`bot.py stats`**: n, винрейт **рядом с безубыточным винрейтом** (средняя полная цена акции),
P&L всего/средний/медианный, σ, ROI, средний выигрыш/проигрыш, payoff, profit factor,
максимальная просадка (в USDC и % от пика с учётом стартового банкролла), максимальная серия
убытков, Sharpe-подобные метрики (на сделку: mean/std доходности; по дням: календарные дни с
нулями, ×√365 — при < 30 днях помечается как неустойчивая), сколько P&L ожидала модель против
полученного. Разбивки по активу, длительности, стороне, maker/taker, цене входа, времени до
закрытия. При n < 100 — явное предупреждение.

**`bot.py hypothesis`** — отличим ли наблюдаемый edge от нуля.

Нулевая гипотеза учитывает реальную асимметрию выплат: сделка, купленная по полной цене c
(с комиссией), платит (1 − c) при выигрыше и теряет c при проигрыше. «Edge нет» означает, что
цена была справедливой: **H0: P(win_i) = c_i**, E[P&L] = 0. Поэтому покупка фаворитов по 0.97 с
97 % побед — это и есть H0.

| # | тест | что проверяет |
|---|---|---|
| 1 | число побед против распределения Пуассона-биномиального с p_i = c_i (точно до 2000 сделок, дальше — нормальное приближение с поправкой на асимметрию) | биномиальный тест винрейта, где у каждой сделки свой безубыточный винрейт |
| 2 | суммарный P&L: z-тест (Var = Σ shares²·c(1−c)) **и** Монте-Карло под H0 | P&L с учётом размеров ставок; Монте-Карло нужен, потому что выплаты фаворитов сильно скошены |
| 3 | кластерный бутстрэп (по часу по умолчанию, `--cluster window/day/trade`) | ДИ среднего P&L и ROI без предположения о независимости: одновременные окна (BTC 5m и 15m, BTC и ETH) коррелированы, и тесты 1–2 это переоценивают |
| 4 | калибровка модели: победы против Пуассона-биномиального с p_i = P(fair) | модель переоценивает вероятность? Тогда показанный ею edge завышен |
| 5 | мощность | минимальный обнаружимый средний P&L при текущем n и сколько сделок нужно для текущего среднего (α, мощность 80 %) |
| — | винрейт против 50 % | только **контраст**: этот тест цены не учитывает и ничего не доказывает |

Вывод «положительный edge статистически отличим от нуля» делается, только если тесты 1 и 2
(нормальный и Монте-Карло) значимы на уровне α **и** нижняя граница кластерного бутстрэпа > 0.
Симметрично — вывод об отрицательном edge. Разбивки по активу/длительности — разведочные, с
поправкой Холма. `--json` выдаёт результат машиночитаемо.

Проверено тестами: при нулевом edge вывод «edge > 0» срабатывает не чаще ~α (60 прогонов);
реальный edge +6 п.п. на 1500 сделках обнаруживается; сценарий «98.2 % побед по цене 0.985 +
комиссия» — тест против 50 % даёт p < 1e-100, а проверка гипотезы корректно не видит edge
(P&L отрицательный).

**Еженедельный отчёт** (`data/reports/weekly_*.md`): работающий бот (shadow/paper) раз в час
проверяет, прошло ли 7 дней с прошлого отчёта (`data/report_state.json`; первый запуск только
запускает отсчёт). В отчёте — paper-сделки за период и с начала, разбивки, качество исполнения
(отправлено/сброшено по причинам, задержка p50/p95, fill ratio), сигналы и частые гейты,
теневые результаты сигналов, проверка гипотезы по всем закрытым сделкам. `bot.py report` —
сформировать сейчас.

### Бэктест

`shadow --record` / `paper --record` пишут сырые фреймы всех фидов + снимки discovery + исходы в
`data/ticks/ticks-*.tsv.gz` (ротация раз в час). `replay` прогоняет их через **те же**
парсеры, hub и движок с `ReplayClock`; все задержки исполнения (перечитывание книги, доставка
ордера, таймаут мейкера) идут через `ReplayScheduler` в виртуальном времени. С `--paper` —
свежий paper-счёт в каталоге результатов, не зависящий от kill-switch живого бота. REST в replay
не используется: K для Binance-окон берётся из записанного потока сделок, а перечитывание
книги — это локальная книга через `PAPER_REFRESH_LATENCY_MS`.

## Инфраструктура

* VPS ближе к инфраструктуре бирж (обычно Европа — например, Франкфурт/Дублин; уточняйте по
  задержкам к `stream.binance.com` и `ws-subscriptions-clob.polymarket.com` со своего сервера).
  Бот хостинг не покупает и не настраивает; все эндпоинты — параметры.
* **Синхронизация времени обязательна** (chrony/NTP): τ в последние секунды окна считается от
  локальных часов. Бот сверяется с Binance каждые `CLOCK_CHECK_INTERVAL_S` и включает гейт
  `clock_skew` при расхождении.
* Binance блокирует часть юрисдикций; при необходимости используйте `BINANCE_WS_URL` зеркала.
* `orjson` (есть в requirements) ускоряет разбор JSON. `uvloop` — по желанию: `pip install uvloop` и
  `USE_UVLOOP=true`; по умолчанию выключен, потому что под uvloop отмена ещё не установленного
  WebSocket-соединения (при остановке) порождает безвредную, но шумную ошибку внутри websockets.

## Допущения, которые нужно подтвердить на живых данных

Код писался и тестировался в среде без доступа к биржам: фиды проверены на фреймах в
документированном формате и на локальном WS-сервере, но не на реальных эндпоинтах.
Всё ниже сделано fail-closed — при несоответствии окно не торгуется, а не торгуется «как-нибудь»:

1. Формат подписки RTDS `crypto_prices_chainlink` (фильтр `{"symbol":"btc/usd"}`) и наличие
   символов для DOGE/BNB.
2. Поддержка `"operation": "subscribe"` на CLOB market channel (есть автоматический откат на
   переподключение).
3. Поле price-to-beat в Gamma (`eventMetadata.priceToBeat`) — используется, только если есть (публикуется
   примерно через минуту после старта окна, поэтому для live-бота K обычно считается из тиков Chainlink).
4. Правила резолюции **дневных** окон (какая свеча/время): пока не определены → такие окна
   обнаруживаются и логируются, но не оцениваются (`reference_rule_unknown`).
5. Выравнивание 4h-окон — берётся из слага, не вычисляется.
6. Формат ответа REST `GET /book` (уровни парсятся без расчёта на порядок сортировки) и
   поведение `last_trade_price` для мейкер-симуляции (учитываются только сделки по нашему токену).

Первый запуск: `python bot.py discover`, затем `shadow` на 30–60 минут и просмотр статусных
строк (`unpriced` / `gates`) — они сразу покажут, какое из допущений не выполнилось.

Первый запуск paper: `python bot.py paper` на несколько часов, затем `analyze` — в разделе paper
видно, сколько сигналов сброшено и почему (бюджет задержки, устаревшая книга, сигнал ушёл после
перечитывания), и какая задержка сигнал→отправка реально получается с вашего сервера.

*Не является финансовой рекомендацией. Результаты сигналов и paper-торговли — фактические
метрики за пройденные окна, без каких-либо гарантий.*
